**结论先说：不通过。**

提交说明里「随机 12000 副 100% 一致」这个数字本身没有造假，但它度量的东西不是「算番正确」。
我重新生成了一批**提高稀有番种比例**的牌型（5913 副合法和牌），总分一致率只有 **81.7%**。

## 一、必须修的问题

复现方式：所有牌例都可以直接喂给 `scratchpad/rv/probe.swift`（格式 `手牌 和牌张 副露 门风 圈风 自摸`），
oracle 用 `scratchpad/rv/orc.py`。「官方」= PyMahjongGB；括号里注明规则依据时，
引用的是**本次提交自己加进来的** `Tests/data/mcr_reference.md`。

### M1. 九莲宝灯判定不看和牌张 —— 单副最多多算 61 分（严重）

`mcrIsNineGates(_ freq:melds:)`（`MCRScoring.swift:440`）只检查**和牌后 14 张**是否符合
`1112345678999 + 1`，完全没有把和牌张摘出去。九莲宝灯的定义是**和牌前那 13 张**必须是
`1112345678999`，和牌张才是「见任一张即和」的那张。

| 牌例 | 我们 | 官方 |
|---|---|---|
| `11112345678999m` 和 `2m` | **106**（九莲宝灯88 + 四归一2 + 清龙16） | **45**（四归一2 + 幺九刻1 + 清一色24 + 清龙16 + 门前清2） |
| `11123445678999p` 和 `9p` | **89** | **28** |
| `11122345678999m` 和 `1m` | **89** | **29** |

摘掉 `2m` 后剩下 `1111345678999m`，不是九莲的十三张，官方判普通清一色。
规则依据：`mcr_reference.md:68`「门清一种花色 1112345678999，九面听，**见该花色任一张即和**」。

在我的稀有型加权集里，这一类命中 **432 副**，是最大的单一错误来源。

### M3. 排除表是「整条删」，和新的顺子配对图模型自相矛盾 —— 少算

这是本次改动**新引入**的不一致。`mcrChowPairFans` 现在按边选番，允许一副顺子既参与大结构番
又参与配对番；但 `mcrFinalize` 用的 `mcrFanExcludes` 仍然是**整手牌一刀切**：

```swift
"一色三步高": ["连六", "老少副"],
"清龙":      ["连六", "老少副"],
"三色三同顺": ["喜相逢"],
"一色三同顺": ["一般高"],
```

于是「大结构番之外那副**没参与**的顺子」凑出来的番也被删掉了：

| 牌例 | 我们 | 官方 |
|---|---|---|
| `11m234455666778p` 和 `4p` | **21** | **22**（一色三步高16 + **连六1** + 平和2 + 缺一门1 + 门前清2） |

我把调试打印注进 `mcrChowPairFans` 验证过，模型本身**算对了**：

```
DBG edges=0-2:连六 used=[0,1,3] idx=[0,1,2,3] -> ["连六"]
```

连六来自 `234p` 与 `567p`，而 `234p` 根本不在一色三步高（`456/567/678`）里，
按原则 3「已组合过某番种的**那些牌**不能再组成相同番种」它应当保留。是排除表把它删了。

同一个 bug 还有一个更隐蔽的形态：**打分时没考虑排除表，平局时会挑一个注定要被删的番**。

| 牌例 | 我们 | 官方 |
|---|---|---|
| `123m12344p112233s` 和 `1p` | **24** | **25**（三色三同顺8 + **一般高1** + 小于五12 + 平和2 + 门前清2） |
| `123445566789m11p` 和 `1p` | **22** | **23**（清龙16 + **一般高1** + …） |

调试输出显示模型在 `一般高`（1 分）和 `喜相逢`（1 分）之间挑了 `喜相逢`——两者同分，
`if pts > bestPts` 保留先找到的那个——然后 `三色三同顺 → 喜相逢` 把它删成 0。
`mcrChowPairFans` 必须在**排除之后**的分值上做最大化，否则这类平局会持续掉分。

在只含 4 副顺子的 2500 副专项集里，这一族造成 **27 副总分不一致**（另有 35 副只是番种名不同）。

## 二、逐条回答你点名的 5 处

### 1. 顺子配对番的图模型 —— 模型本身站得住，但落地是错的

「无环 + 同名边不共点 + 大结构番占用的面子先并成一个分量」这三条我用 2500 副纯 4 顺子牌型
对着 oracle 验过：**总分只有 27 副不一致，而且这 27 副的根因全部是 M3（排除表 / 平局挑番），
不是图模型本身**。规则书两个判例（`234567筒 234567条`、`234条 223344567筒`）我复跑都过。
`123m123p44s + 吃123m + 吃123p` 这类「一般高×2 + 喜相逢」的判例也过（我们出
`一般高1 + 喜相逢2`，官方出 `一般高2 + 喜相逢1`，同为 3 分，参照报告把两者都列为合法 ALT）。

所以：**模型是对的，但因为 `mcrFanExcludes` 没有跟着改成「按面子」而是仍然「按整手牌」，
这次改动只兑现了一半**。提交说明里「官方允许共用」的论断对，但只对 `三色三步高 + 一般高`
这种「大番不排除小番」的组合生效；一旦大番在排除表里点了小番的名（清龙/一色三步高/
三色三同顺/一色三同顺），共用又被吃掉了。这是本次改动**新引入的自相矛盾**。

另有 35 副（2500 中）总分对、番种名不同（连六 ↔ 老少副 ↔ 喜相逢 的等价平局）。
分数无碍，但 `MCROracleTests` 是按**番种集合相等**断言的，将来扩样本必炸。

### 2. 独听判定 —— 理由成立，实现基本正确，有一处理论隐患

「不能用 `mcrCalculateWaiting`」这个理由**成立**，我验证过：
`mcrCalculateWaiting`（`MCRCalculator.swift:385`）确实有 `guard base[i] + meldFreq[i] < 4`。
构造牌例 `123s77z 和 1s，明杠4s + 吃123m + 吃123p`：`23s` 形状上听 `1s/4s`，
而 4 张 `4s` 全在自己的杠里。我们不给边张，**官方也不给边张**（两边同为 9 分）。
说明官方同样按「形状」而非「摸得到与否」判独听。这一条改对了。

特殊型走不走这条路径：`isUniqueWait` 的过滤在 `consider()` 里，对**所有分支**生效，
包括七对/十三幺/全不靠/组合龙/九莲。实际上 七对/十三幺/全不靠/七星不靠 都在排除表里
把 `单钓将` 删掉了，所以过滤是空转；组合龙/九莲分支传的是 `singleWait: false`，
本来就不产听牌番。**没有发现由此产生的错误**。

两处隐患（未观察到实际错分，供参考）：
- `mcrIsCompleteHand` 在 `melds.isEmpty && sum == 14` 时会把七对/十三幺/全不靠也算作和牌
  （`MCRCalculator.swift:223-227`），所以「标准型听 A、七对听 B」的手牌会被判成听两张。
  这大概率**正好是对的**（官方也遍历 34 张），但它是一个未经验证的耦合。
- `trial[i] += 1` 没有 `guard concealed[i] + meldFreq[i] < 4`，当某张已有 4 枚时会构造出
  5 枚的非法频次数组丢给 `mcrIsCompleteHand`。目前没炸，但这是隐式依赖被调用方的宽容。

### 3. 幺九刻扣减 —— 正确，没有减成负数

我针对性构造并对 oracle 验过：
- 三风刻 + 圈风 + 门风 + 111万刻 + 55饼将 → 我们 24，官方 24（幺九刻只剩 1）✔
- 三风刻 + 圈风 + 门风 + 456万 + 99饼将 → 17 / 17 ✔
- 参照报告边界 #2「三风刻减 3 但保留圈风刻门风刻」`111222333z12399p 和 9p 自摸` → 47 / 47 ✔
- 大四喜 `111222333444z55z` → 幺九刻整条排除 ✔（不过这条被 M5 的 +3 污染了，见上）
- 小四喜 `111m44z + 碰东南西` → 106 / 106 ✔（此例被混幺九吃掉幺九刻，扣减逻辑没被触发）
- 字一色 `555z666z77z + 碰东南` → 135 / 135 ✔

减不成负数的原因是 `windPungs ⊆ pungs`，两次扣减的对象互不相交且都是 `yaojiuPungs` 的子集。
逻辑上安全。**这一条我认可。**

### 4. 和绝张的推导 —— 条件充分，不必要，和手动勾选不打架

`concealed[w] == 1 && meldFreq[w] == 3`：
- **充分**。`meldFreq[w] == 3` 只可能来自自己的明刻，或来自多副吃里重复出现的那张
  （例：吃`345m` 吃`456m` 吃`567m`，`5m` 在副露里出现 3 次）。两种情况那 3 张都是**明着**的，
  确实是绝张。我专门造了后一种：`456m77z 和 5m，吃345m/456m/567m` → 我们 30，**官方也 30，
  两边都给和绝张**。参照报告 :500 的 `[456s,1][456s,1][456s,3]45s55m6s = 96番` 含和绝张 4，
  我们也是 96。所以不是误报。
- 暗杠**不算明着**这个顾虑不成立：暗杠占 4 张，`meldFreq[w]` 只能是 4，永远进不了这个分支。
- **不必要**。别家打出的 3 张、别家副露里的 3 张，App 的数据模型里没有，推不出来。
  所以只能覆盖「自己碰了一副再和第 4 张」这一种，其余仍靠用户勾。
- **不打架**：`ctx.lastTileOfKind || lastTileOfKindByCount` 是或运算，自动推导只会加不会减，
  而自动推导又不会误报。唯一的副作用是用户**取消勾选也关不掉**它——但既然自动推导恒真，
  这在正确性上无害。

**这一条我认可。**

### 5. 默认值改动 —— 迁移路径缺失，Android 未同步，而且其中一项改反了

**(a) `mcrJiuLianCountsShuangAnKe` 默认改成 `false` 是错的，方向反了。**
提交说「默认关 = 对齐官方」。官方算番器给的是**计**：

```
11122345678999p 和 2p → 官方 92 = 九莲宝灯88 + 双暗刻2 + 幺九刻1 + 连六1
```

这正是提交自己加进来的 `mcr_reference.md:503` 那条
`11123456789992p = 92番 九莲宝灯88+双暗刻2+幺九刻1+连六1`，:249 行也写着
「九莲宝灯 …… **可另计** 四归一、清龙、**双暗刻**、连六」。
（我们两个开关都给不出正确值，因为 M2 让九莲分支根本产不出双暗刻/幺九刻——
两个 bug 互相遮掩，所以差分测不出来。）

`Tests/MCRScoringTests.swift` 的 O2a/O2b 断言（90 / 88）**两个都是错的**，
正确值是 91（开）/ 89（关）——而且这两个值我们现在一个都算不出来。

字一色不计混幺九、三杠不再单计每个杠这两项我验过，**方向是对的**
（`222333444z55566z` → 143 一致；三杠 `123m11p + 2杠` → 69 一致）。

**(b) 老用户没有迁移路径。**
`RuleSettingsStore`（`MahjongScoring.swift:199`）用 `UserDefaults` 键 `ruleSettings.v1`
存整份 JSON，`didSet` 时全量 `encode`。也就是说：

- 从没动过任何设置的用户 → 无存档 → 吃新默认值 → 行为改变（这是想要的）。
- **动过任何一项设置的用户**（哪怕改的是底分、玩法这种无关项）→ 存档里这三个键存在且为 `true`
  → `decodeIfPresent(...) ?? false` 读到 `true` → **永远停在被提交自己定性为「算错」的旧行为上**，
  没有任何提示、没有版本号、没有迁移代码。

`storageKey` 还是 `ruleSettings.v1`，说明作者也没打算做版本迁移。既然提交的立场是

## 四、存疑但不确定的

1. **组合龙手牌算不算平和？** 官方给 `平和2`（`258m233469p14788s 和 3p` → 17；
   `147789m36999p258s 和 8s` → 16）。参照报告 :293 / :354 也说组合龙「可另计平和」。
   但 1998 规则原文的平和是「四副顺子 + 序数牌将」，组合龙的龙身不是顺子。
   官方算番器把龙身当顺子处理，属于实现口径。**我按 oracle 记成缺陷（M2），但如果你的
   基准是规则原文而非算番器，这一条可以不改。** 注意参照报告自己也标了
   「258m23469p14788s 3p = 16番 / ALT 17番 ← 注意两种拆法总分不同」，说明连参考实现之间都有分歧。

2. **清幺九是否排除双同刻（M8）？** oracle 排除，81 番排除表里我没找到明文依据。
   同理 `一色四同顺 → 四归一` 参照报告 :358 有明文，`清幺九 → 双同刻` 没有。
   置信度低于其它几条。

3. **`边张` / `坎张` 在多解法下的选名。** `677889s 和 7s` 可读成 `678+89听7`（边张）
   或 `789+68听7`（坎张），同为 1 分，我们选坎张、官方选边张。分数不受影响，
   但如果你要 100% 复刻官方的番种列表就得对齐拆解优先级。3000 副随机集里出现 7 次。

4. **稀有型加权集的 81.7% 不能直接和提交里的 100% 比。** 我的生成器刻意把
   九莲/七对/组合龙/字一色/绿一色 等提到了 ~50% 的比例，是**为了打盲区而设计的分布**，
   不代表真实牌局。它说明的是「盲区里几乎全错」，不是「引擎整体 18% 错」。

## 六、明确结论

**不通过。**

按「与国标规则完全一致」这个标准：

- **改对的部分是实打实的**：幺九刻扣减、独听要求、三杠/字一色默认值、排除表补的那批
  「必然并存」、和绝张推导、三色三节高不再吃双同刻、双暗杠不再计双暗刻——我逐条验过，
  这些方向都对，且被 oracle 和参照报告双重佐证。顺子配对图模型的**思路**也是对的。
- **但仍有 8 类可复现的算错**（M1–M8），其中 M1 单副最多多算 61 分、M2 单副最多少算 62 分、
  M7 会让不够起和的牌被判成能和。这些都不是边角料：七对、十三幺、九莲宝灯、组合龙、
  自摸——正是普通用户最会拿去对分的牌型。用户投诉的「计番不全不准」，
  在特殊型这一支上基本原封不动。
- **M3 是本次改动新引入的自相矛盾**，不是遗留问题：图模型按面子发番，排除表按整手牌删番。
- **O2a/O2b 两条测试把 bug 固化成了期望值**，和提交声称的「逐条用 oracle 判定」不符。
- **默认值改动没有迁移路径**，受影响最大的老用户拿不到修复；**Android 端完全没跟**，
  双端现在会给出不同的分。

**给一个可执行的收尾顺序**（按性价比）：

1. 把 `Tests/data/mcr_reference.md` 里那 32 条手工例题 + 23 条杠矩阵**直接变成测试**。
   它们是现成的、来源可靠的、且正好落在盲区上。现在报告在仓库里躺着，没有一条被断言。
2. 修 M1（`mcrIsNineGates` 传入 `winningTile`，先摘掉再判 13 张）。
3. 给五条特殊型分支补上 `mcrHonorFan` / `mcrConcealmentFan` / `mcrCompositionFan`（M2）。
4. 把 `mcrFanExcludes` 从「整手牌」改成「按参与面子」，或至少让 `mcrChowPairFans`
   在排除后的分值上最大化（M3）。
5. `mcrFinalize` 改成迭代到不动点，或先删再算 victim（M4）；补 `四暗刻/七对/九莲宝灯 → 不求人`（M5）。
6. 补 `绿一色 → 混一色`（M6）；`coreTotal` 不再跳过 `自摸`（M7）。
7. 把 `mcrJiuLianCountsShuangAnKe` 默认改回 `true` 并修正 O2a/O2b 的期望值（91/89）。
8. 重新生成差分集时：**自摸随机、特殊型按番种配额构造**，而不是靠随机 4 面子撞。
   一致率报告里请分开列「均匀随机」和「稀有型加权」两个数。
9. 决定 `明暗杠` 和 Android 的口径：要么 Android 跟改，要么 iOS 这边加版本迁移；
   两端字段不一致这件事不能就这么放着。
